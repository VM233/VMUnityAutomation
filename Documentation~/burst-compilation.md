# Native Burst recompilation after a managed rebuild

An explicit `asset/refresh` request may set `recompileBurst:true`. The existing durable workspace job first completes its normal C# compilation and assembly reload, then requests recompilation through Unity's integrated Burst compiler and waits for completion. This option requires Unity 6000.6 or newer and an enabled integrated Burst compiler. Omission preserves the existing C#-only contract. It changes neither Burst options nor project assets and does not reopen any Editor window.

The observed failure was a successful managed job following an earlier failed dependent-assembly compile. Scheduled voxel jobs still executed a native DLL older than the changed job layout: the first palette bytes were interpreted as a NativeArray length, and all tree raster outputs were empty. C# diagnostics, reload and source/IL inspection cannot prove native adoption. The operation uses the compiler's recompilation entry point, also used by its native options owner, with one original job identity. Unity alone owns the paired managed/native domain lifecycle. It never changes a job name, rearranges fields to fit stale code, disables Burst, or substitutes managed execution.

Do not use this option in versions 0.6.281 or 0.6.282. Those versions additionally issued a native DomainReload after the managed reload had already completed. Subsequent Play Mode startup crashed with an ECS sorting direct call entering a different compiled function. Version 0.6.283 removes that second domain reset. A crashed Editor must be recovered before validating current scheduled kernels; a completed compiler request alone remains insufficient evidence.

The workspace job owns one native request timestamp, its assembly-domain revision and a completion timestamp. It publishes the request before invoking the native owner, observes completion without reissuing, and fails if a new domain reload interrupts the native phase. A 600-second deadline bounds observation; timeout is a terminal failure, not a retry. Unity's native completion predicate indicates that its compilation queue finished; it does not indicate that every native compilation succeeded.

An opted-in job therefore persists a separate `burstDiagnostics` window before AssetDatabase refresh can trigger managed compilation. The window survives reload and includes eager Burst diagnostics before managed completion, diagnostics emitted during reload, and diagnostics emitted by the explicit native recompilation. Its endpoint is frozen after native completion. `Burst error BC1055` and warning headers are retained with original text, optional source location and absolute Editor-log byte offsets even when no managed source-assembly mapping exists. Each header's `followingLogText` retains all following log lines through the next native diagnostic or the frozen endpoint, preserving CRLF and multiline native details. This is surrounding log context, and may include unrelated Editor messages; it is not attributed wholesale to the native compiler. C# counts remain the managed diagnostic product; they cannot establish native success. The native window has its own revision, byte boundaries, capture completeness, error/warning counts and entries in the durable job, success result and native-failure details.

Any captured native error produces `burst_compilation_failed`. Missing identity, log access failure, path changes, replaced/truncated/rewritten boundaries, invalid UTF-8, a partial line at either endpoint, unrecognized native diagnostic grammar or exceeded capture budgets produce `burst_compilation_diagnostics_incomplete`. Retained messages in an incomplete product are partial evidence only. The window owns no persistent file handle or callback subscription; both boundary and final reads dispose their streams. Cancelled or interrupted jobs retain their recorded start boundary and do not claim a completed capture. `captureComplete` means the frozen byte window was read completely; it is not an acknowledgement of unexposed native logging buffers. In Unity 6000.6 the Editor Burst loader enables eager logging and the eager callback directly calls the native logger, with no managed deferred publication. The managed completion API exposes no separate log-flush acknowledgement, so no sleep or extra polling is used to invent one. Actual scheduled-kernel regressions remain required for behavior and native adoption acceptance; successful diagnostic capture does not prove the compiler loaded the intended assembly metadata.

Static Cost Ledger before diagnostic-window executable writes: two exact reflected native methods resolved once per domain; one native request and the existing completion polling deadline per opted-in refresh. One persisted log window starts before the refresh can trigger managed compilation and ends after native completion. Its explicit capture budgets are 64 MiB of appended UTF-8 log bytes, 262,144 lines, 64 KiB per line, 1,000 native diagnostic records and 1 MiB of retained diagnostic text including surrounding context. Exceeding any budget is `burst_compilation_diagnostics_incomplete`, never a successful partial report. A forward reader uses two 64 KiB byte buffers, at most 1,024 full blocks (short reads consume the same byte budget), at most 67,108,864 bytes of forward scanning and 262,144 line decodes. Header/location parsing uses a fixed number of ordinal linear scans and a digit scan; no backtracking regex or pairwise deduplication is used. Context is appended through one reusable StringBuilder, never repeated whole-string concatenation. Peak capture buffers, context construction and retained text/maps stay below 6 MiB; a completed product retains less than 4 MiB, with at most 200 jobs retained by the existing store (less than 800 MiB if every retained job reaches every limit). Total decoded text is bounded by 128 MiB plus at most 262,144 string headers over one scan. Two boundary hash reads inspect at most 512 bytes and the begin-line check reads one byte. A 256-byte boundary hash plus file creation identity detects replaced, truncated or rewritten boundaries across reload. No asset/source scan, timer, worker, transport, binary copying or cache deletion is added. Capture runs once on the Editor main thread after native completion; these finite I/O and memory bounds are explicit diagnostic budgets, while native timing remains to be measured. There is no claim that the 600-second native wait or the log I/O is free Editor overhead.

Focused regressions cover persistence through real JSON serialization, eager and post-reload errors in one window, previous-cycle exclusion, native errors despite zero managed errors, unknown source paths and missing locations, warning counts, rewritten and missing logs, invalid or incomplete text, and all capture budget boundaries. The native package test fixture is `VMUnityAutomation.Editor.Tests.VmBurstCompilationDiagnosticsTests`; the existing `VmAutomationBurstCompilationTests` covers the request lifecycle and public contract. Offline execution can verify pure diagnostic logic, but installed-package compilation, native test execution and an official `asset/refresh` replay remain separate acceptance steps.
