# Cooperative project tool resource retirement

An incremental tool implements `IVmProjectToolAsyncCleanup` when its native objects, callbacks, source Tasks or worker Tasks can outlive a job step. The running step captures `VmProjectToolExecutionContext.CaptureCancellationCheck()` and first publishes `PublishCleanupToken(actualToken, actualRetirementTask)`. The Task is the owner's prepublished `Task<VmProjectToolCleanupReceipt>`; source work and a trace writer start only after admission. The original job record owns cancellation and this capability. The SDK does not register another scope or wrap that Task.

`CleanupJobAsync(actualJobID, actualCleanupToken)` requests the actual owner to cancel and retire its work, then returns the identical admitted Task. If that Task is already terminal, the SDK consumes its receipt without looking up a destroyed or reused scope. A request for a running admitted job starts cancellation and leaves its cleanup running while the Task is pending. Later cleanup requests observe the same work. Other accepted jobs retain their original queue order and cannot execute while this resource owner is retiring.

The receipt binds JobID and CleanupToken, freezes the actual result into transport-safe immutable data, and carries ResourcesReleased independently from Failure. The original exception is retained internally; `ThrowIfFailed()` rethrows that same object for source owners. Public Failure uses the existing stable SDK error response, never reflected Exception properties. The Result is still the original cleanup tool's domain product and is validated against that tool's closed output schema. Cleanup succeeds only when the actual receipt proves resource release and contains no failure. A failed operation may have released all resources; a terminal or canceled job alone does not prove release.

The runner first reads the original Task's terminal product, then adopts its exact identity and validates its domain result. A foreign identity does not publish a release receipt for the admitted job. The actual source failure remains the first failure; request, identity and schema failures are retained as secondary errors in the stable SDK error product. An identity-qualified receipt may independently prove release even when its domain result fails schema validation.

Cancellation observation remains attached until every actual source, native lease, callback and worker writer has retired. Play Mode exit and compilation intent request the same retirement. Normal completion also joins it. A source or callback error must not stop attempts to retire independent resources. Publish the final product only after those attempts and final observations. Never synchronously wait for a pending frame, procedure or trace Task on Unity's main thread.

For controlled reload, cancel the owning job, request its asynchronous cleanup, and poll `jobs/get` until its admitted Task's receipt has been published. Then invoke the existing `jobs/repair-history` reload request. Its gate checks current-lifetime admission facts persisted by the runner: released receipts, requests that never entered source work, and historical unknown owners are separate products. Old jobs are never retroactively classified by a current descriptor or assumed released because they completed without an error. The SDK gate covers this actual controlled reload producer. Unrequested third-party script reload or forced destruction can interrupt work and remains an unknown-release observation; no reload lock is installed.

Contract discovery remains the bounded catalog. `asyncCleanupContract` identifies qualified project tools and job snapshots; resourceOwnerLifetime ties a new admission to its actual runner domain. Detailed input/output schemas and error codes come from the descriptor and generated job/history contracts. Existing incremental state, capture predicate and execution/history retention bounds remain unchanged. Focused tests use the real runner publication, actual Task and receipt, a scoped isolated record store, and restore their original private state. Official package test products provide their execution evidence separately from this API contract.
