# Incremental job persistence

Profiler frame `3301` in the MarbleBattlers Editor capture of 2026-09-12 attributes 525.053 ms and 50.4 MB of allocations to `VmAutomationPersistentJobRunner.Tick`. Frames `3194` and `3198` repeat the same 50.4 MB allocation. Every step serializes the full retained execution list and the full published history before and after the project callback, even when only one small progress record changes. The frozen store has 200 execution records (1,859,996 bytes, largest 127,166 bytes) and 200 history records (1,241,289 bytes, largest 126,938 bytes). This is distinct from the sandbox preparation and first-use asset loading stalls.

Entry points are start, progress, cancellation, completion, cleanup and reload recovery. The persistent runner remains the sole execution-state writer. JobHistory remains the sole owner of immutable public snapshots and access capabilities. A shared record store owns only atomic JSON persistence. Each job type and ID names one hashed record. Updating a job serializes and replaces that record only. An ordered index owns membership, with atomic replacement only when membership/order changes. Removed record files retire after index publication. Existing public commands, tokens, job identity, cancellation and interrupted-job semantics remain unchanged.

The existing aggregate file is migrated once when no record index exists. All records are written before the index is published, then the aggregate file retires. An interrupted migration has no published index and therefore reuses the original aggregate input. Once the index exists it is the sole authority, including after a process exit between index publication and aggregate retirement. Missing indexed records or invalid JSON fail at the store boundary. There is no history purge, deferred durability, background write, delayed progress or alternate transport.

Static Cost Ledger before executable writes: the frozen calibration has 200 records per owner and one changed record per progress publication. At most four changed-record serializations and atomic file replacements per ordinary runner step replace four full-store serializations. Each identity is at most 96 UTF-8 bytes in this frozen input, yielding at most 804 bounded SHA-256 operations and 77,184 input bytes per step. Largest changed-record admission is 128 KiB here, giving at most 512 KiB serialized payload per step (the current progress records are below 8 KiB). Existing history retention supports up to 2,000 records and execution retention is 200; index traversal remains linear, at most 4,404 identity hashes across both publications and below 512 KiB index/identity scratch. Membership changes serialize at most a 134 KiB index for that declared maximum. No Cartesian product, per-record Unity calls, physics work or native asset operations. Retained store state contains index strings only, below 512 KiB at maximum retention, plus the already-owned job dictionaries. All file replacements keep the existing flushed temporary-file publication and path lock. Migration is a single bounded load of the original files and one write per retained record, outside calibration sample execution. A load also visits at most the retained records plus the one interrupted membership publication to retire unindexed record files.
